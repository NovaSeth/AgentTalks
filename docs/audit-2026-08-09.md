# AgentTalks audit - 2026-08-09

> Historical audit: the findings have been tracked and fixed since; see [NEWS.md](../NEWS.md).

Method: 12 independent perspectives read the code in parallel, and EVERY reported
finding received its own skeptic tasked with **disproving** it. Of 139 reports,
**116** survived verification; 23 were rejected (17%) because the code either did
not do what was claimed, a safeguard existed elsewhere, or the scenario was
infeasible. In total: 151 agents, 8.1 million tokens, 3308 tool calls.

This file records the INITIAL STATE: the list of problems from which the work
began. It serves to check whether anything was missed and to understand why
individual changes take the shape they do.

## Security and identity (18)

### [high] Revoking a token and disabling an account do not close an open SSE stream
**File:** `src/http/sse.ts:34`  
**Issue:** sseHandler checks identity EXACTLY ONCE, when establishing the connection (requireAuth at line 34), then subscribes to the event bus (bus.subscribe, line 104) and lives until the socket disconnects. Nothing subsequently checks whether the token still exists or the actor has been disabled: the ping every 20 s (line 110) merely KEEPS the connection alive, and EventBus has no mechanism for closing an actor's subscriptions (src/core/events.ts: the only removal is unsubscribe called by the client itself). Consequently, revokeToken (src/core/tokens.ts:136) and setDisabled (src/core/actors.ts:105) affect only the NEXT HTTP request, while an already established stream sends no further requests.  
**Scenario:** Agent @nestor's token leaks (for example, from a CI log). Someone opens GET /api/events with this token and leaves the connection open. An admin executes DELETE /api/admin/tokens/17 or disables the actor in the panel: the UI confirms revocation, and subsequent POST requests with this token receive 401. But the open SSE stream continues receiving EVERY new message from all conversations @nestor belongs to, in real time and without a time limit, until the server process restarts. The same applies to a disabled human account: POST /api/admin/actors/5/disable does not interrupt its tab with an open SSE connection.  
**Fix:** Revalidate identity in the ping cycle (every 20 s) and terminate the stream when it is no longer valid: in the setInterval callback at line 110, call authenticate(rc.ctx, rc.config, req) again and execute res.destroy() on null (the same applies to long polling, which can hang for 300 s). A stricter variant: add an EventBus closeActor(actorId) method called by revokeToken and setDisabled. Add a test: token -> open SSE -> revokeToken -> stream ends within one ping interval.

### [high] SSRF: an IP literal bypasses guardedLookup, and assertPublicHost does not recognize IPv4-mapped IPv6 addresses
**File:** `src/core/wake.ts:79`  
**Issue:** The comment next to isBlockedIp/guardedLookup says the SSRF check at delivery time is AUTHORITATIVE. It is not: node:net completely skips the `lookup` option when the host is an IP literal (confirmed experimentally: lookup was never called, and the connection to 127.0.0.1 succeeded). For such addresses, the only defense is the regex-based assertPublicHost at registration, and it has three holes: (1) IPv4-mapped IPv6 addresses: `new URL('http://[::ffff:169.254.169.254]/')` produces hostname `[::ffff:a9fe:a9fe]`, which matches none of the patterns; (2) 100.64/10 (CGNAT); and (3) 0.0.0.0/8 except 0.0.0.0 itself: both appear in isBlockedIp but not assertPublicHost. Furthermore, isBlockedIp itself handles only the dotted form `::ffff:127.0.0.1`, not the hexadecimal form `::ffff:7f00:1` produced by the URL parser, so even if lookup were called, it would still let it through.  
**Scenario:** PUT /api/wake {"target":"http://[::ffff:127.0.0.1]:8080/hook"}: setWake ACCEPTS the address (verified: four variants, including `http://[::ffff:169.254.169.254]/latest/meta-data/`, `http://100.64.0.1/hook`, and `http://0.0.0.1/hook`, all pass without an exception). Every subsequent DM to this actor causes a POST from the server to 127.0.0.1:8080 or the cloud metadata endpoint. This is blind SSRF, but the 2xx/error result is visible through GET /api/wake (the wake_failures counter), so it also works as an internal port scanner. The existing test 'wake rejects local and private addresses (SSRF)' checks only dotted forms, leaving the vulnerability invisible to the suite.  
**Fix:** Normalize the address BEFORE deciding: in assertPublicHost and isBlockedIp, recognize IPv4-mapped IPv6 in hexadecimal form as well (`::ffff:7f00:1`) and reduce it to IPv4 (for example, split the last two groups into bytes), rather than using only the regex `^::ffff:(\d+\.\d+\.\d+\.\d+)$`. Ideally, eliminate the two separate rule lists: for `net.isIP(host) !== 0`, assertPublicHost should call isBlockedIp DIRECTLY (automatically covering 100.64/10 and 0.0.0.0/8), keeping the existing inexpensive layer for names. In httpDeliver, additionally check `net.isIP(url.hostname)` before sending and reject blocked IPs, because guardedLookup never runs for a literal. Add test cases for `[::ffff:127.0.0.1]`, `[::ffff:169.254.169.254]`, `100.64.0.1`, and `0.1.2.3`.

### [high] Private channel content leaks to a nonmember through the notification center
**File:** `src/core/messages.ts:174`  
**Issue:** resolveMentions looks up handles GLOBALLY, without checking membership. A row in the `mentions` table for an unrelated actor is harmless because mentionsOf filters by read permission (and explicitly comments on this: 'a mention in someone else's private channel MUST NOT provide a channel for content leakage'). But the same `mentioned` list goes to notify() together with excerptOf(body), while listNotifications has no access filter because a notification holds a COPY of the content. Consequently, the one deliberately protected path is closed, while the adjacent one remains wide open.  
**Scenario:** Alice creates private channel #secret (bob is not a member) and writes: '@bob the production password is hunter2'. Confirmed by a test: mentionsOf(bob) = [], search(bob,'hunter2') = [], but GET /api/notifications as bob returns {kind:'mention', from:'alice', conversationId:1, messageId:1, excerpt:'@bob the production password is hunter2, do not tell anyone'}. Bob receives the full content (up to 160 characters), plus proof that the channel exists and the message ID. The same path works for every private channel where the attacker knows the victim's handle: ANYONE inside need only write @handle.  
**Fix:** In postMessage, filter notification recipients to those permitted to read the conversation: for a channel (not direct), `actorIds: mentioned.filter((id) => canRead(ctx, input.conversationId, id))`; canRead already allows everyone for a public channel, so behavior there does not change. Alternatively (stronger, because it also protects future notify calls), filter inside notify() itself whenever conversationId is provided. Add a test mirroring the existing one for mentionsOf.

### [high] Deleting a message with a file does not delete the file: its bytes remain downloadable
**File:** `src/core/messages.ts:288`  
**Issue:** deleteMessage knows only the messages table. For a kind='file' message, the files row (deleted_at NULL) and bytes on disk remain. Moreover, messageFromRow does NOT clear `meta` on deletion, so the API still returns {fileId, name, size} for the deleted message. The UI hides this (it checks deletedAt), but the HTTP contract does not, and the file is directly accessible anyway. Deleting a message and deleteFile are currently two independent operations, which the user does not know: 'delete' on a message in the UI looks like deletion of the attachment.  
**Scenario:** Alice uploads private.png to #general and deletes the message shortly afterward. Confirmed by a test: getMessage returns body='' but meta={fileId:'gVQ...',name:'private.png'}, listFiles for bob still shows 'private.png', and readFile(bob) returns all the bytes. Even without an API client, fileId remains in meta in the /api/conversations/:id/messages response, so GET /api/files/<id> suffices.  
**Fix:** In deleteMessage, within the same transaction: if row.kind === 'file', mark the associated files as deleted (deleteFileRow after `SELECT * FROM files WHERE message_id = ?`) and clear meta (`UPDATE messages SET meta = NULL`). To avoid a messages -> files dependency, expose `deleteFilesOfMessage(ctx, messageId)` in files.ts and call it from deleteMessage, or invert the dependency through a small hook. Regardless of the choice, messageFromRow should return meta: null for deleted_at, because the API currently exposes metadata for deleted content.

### [medium] Session cookie lacks Secure when the instance sits behind a TLS proxy without trustProxy
**File:** `src/http/auth.ts:40`  
**Issue:** Secure is appended to the session cookie ONLY when config.trustProxy is true. These are independent concerns: trustProxy means 'trust X-Forwarded-For when counting limits', while Secure means 'do not send this cookie over HTTP'. The default trustProxy value is false (src/config.ts:62), and the only installation path that enables it is docker-compose.yml:50. The systemd unit generated by `agenttalks install-service` (src/cli/main.ts:505-517) does NOT set AGENTTALKS_TRUST_PROXY, and deploy/instance.env.example does not mention it either. The gate cookie has the same problem (src/http/ui.ts:161).  
**Scenario:** Installation without Docker: `agenttalks install-service --write`, with Apache providing TLS at atalks.example in front of it. trustProxy remains false, so Set-Cookie is `at_session=...; Path=/; HttpOnly; SameSite=Lax; Max-Age=2592000`, without Secure. An attacker on the same Wi-Fi network injects `<img src="http://atalks.example/x">` into any page; the browser connects over plain HTTP and ADDS the session cookie (SameSite=Lax does not protect it, because this is a request to the same domain). The attacker reads at_session from the traffic and takes over the session for 30 days, including an admin account.  
**Fix:** Decouple Secure from trustProxy. Set it when the instance is exposed over HTTPS: `config.baseUrl.startsWith("https://")` or (with a trusted proxy) `req.headers["x-forwarded-proto"] === "https"`, and also whenever the host is not loopback. Browsers treat http://localhost as a secure context, so Secure does not break local work; makeCookie/gateSetCookie need a previously computed `secure: boolean`. Also add AGENTTALKS_TRUST_PROXY=1 to the generated systemd unit and deploy/instance.env.example.

### [medium] Successful logins consume the attempt limit; one passkey login costs two attempts
**File:** `src/http/routes/auth.ts:46`  
**Issue:** checkLoginLimit increments the counter on EVERY endpoint call, regardless of the result, and nothing removes the entry after a successful login. The same bucket (loginAttempts, LOGIN_MAX_ATTEMPTS=10 per 900 s) serves three routes: /api/login (line 110), /api/webauthn/login/options (line 174), and /api/webauthn/login (line 191). The UI client implements passkeyLogin as two consecutive requests (app.js:800 and 811), so one SUCCESSFUL fingerprint login costs 2 of 10 units. Furthermore, /api/webauthn/login/options is unauthenticated, allowing the bucket to be exhausted externally.  
**Scenario:** A team works behind one NAT, with trustProxy=1, so the limiter key is the shared outgoing address. The fifth person to log in successfully by fingerprint during that quarter-hour receives 429 'too many login attempts', although nobody has entered a wrong password. Malicious variant: any anonymous caller sends POST /api/webauthn/login/options with body {} 10 times and blocks login for everyone behind that address for 15 minutes. Worst variant: installation without trustProxy behind a reverse proxy: clientKey then returns 127.0.0.1 for the whole world, so 10 requests block login across the ENTIRE instance.  
**Fix:** 1) Remove the entry on success: call loginAttempts.delete(key) after verifyPassword and verifyAssertion; the limit should count FAILURES, not traffic. 2) Do not count /api/webauthn/login/options toward the same bucket (it is a preparatory endpoint), or give it a separate, more generous one. 3) When the handle is known, key by `ip + '|' + handle`, so one targeted user does not block everyone else. 4) Test: ten consecutive successful logins do not end in 429.

### [medium] DELETE /api/admin/tokens/:id reports success even when it revoked nothing
**File:** `src/http/routes/admin.ts:81`  
**Issue:** revokeToken (src/core/tokens.ts:136) executes `UPDATE tokens SET revoked_at = ? WHERE id = ?` and returns nothing; the route unconditionally responds with 200 {ok:true}. It neither checks the number of changed rows nor includes `AND revoked_at IS NULL`. This project already recognized and solved the same problem for invites: src/core/invites.ts:81-89 returns info.changes > 0, justified by the comment: 'revoked for an invite that does not exist creates a false sense of security exactly when someone is containing a leaked code'. The same principle has not been applied to tokens, which are agents' credentials.  
**Scenario:** An agent token leaks. The admin has the panel open in two tabs, or the list refreshed after someone else's action. They click 'revoke' next to token ID 17, which has meanwhile disappeared together with its actor (ON DELETE CASCADE), or whose ID they entered manually. UPDATE changes 0 rows, the server replies 200 {ok:true}, and the UI shows 'revoked'. The admin closes the incident believing the credential is dead, while the token still works. A side effect: revoking a live token again overwrites revoked_at with a new date, so the audit loses the actual cutoff time.  
**Fix:** `export function revokeToken(ctx, tokenId): boolean { const info = ctx.db.prepare("UPDATE tokens SET revoked_at = ? WHERE id = ? AND revoked_at IS NULL").run(ctx.now(), tokenId); return info.changes > 0; }`, and in the route, `if (!revokeToken(...)) throw notFound("token", "nie ma takiego aktywnego tokenu")` ('no such active token'), exactly as for invites two routes above. Update the CLI call and add a test 'revoking a nonexistent token returns 404'.

### [medium] Cookie sessions cannot be revoked: changing a password leaves old cookies valid
**File:** `src/http/auth.ts:29`  
**Issue:** makeCookie signs only `<actorId>.<wygasa>` ('expires'), while actorFromCookie checks the signature, date, and actor's disabled_at. There is no element that could be invalidated per actor. The comment at lines 26-28 justifies statelessness by saying 'a human session needs nothing more', but it needs precisely the one missing thing: revocation. setPassword (src/core/actors.ts:136) changes the password without invalidating anything; there is no 'log me out everywhere' endpoint either. sessionTtlSec defaults to 30 days (src/config.ts:67).  
**Scenario:** A person leaves a logged-in laptop in a cafe, or someone copies their cookie. The instinctive response, changing the password, does NOTHING: the stolen at_session remains valid for up to 30 more days because the signature includes neither the password nor any counter. The only available measures are disabling the account (which also cuts off its owner) or rotating config.secret in the instance file (which logs out ALL humans). For an admin account, this is the difference between 'I changed my password' and 'the attacker has the admin panel for a month'.  
**Fix:** Add a migration with column `actors.session_epoch INTEGER NOT NULL DEFAULT 0`, include it in the signed payload (`${actorId}.${epoch}.${expiry}`), compare it in actorFromCookie, and increment it in setPassword and a new POST /api/logout-all (with CSRF). Cost: one field in the query that already retrieves the actor (getActor), preserving cookie statelessness. Test: changing the password invalidates previously issued cookies.

### [medium] Deployment script passes the gate password on curl's command line
**File:** `deploy/deploy-production.sh:106`  
**Issue:** Gate verification builds the request body using `--data "$(printf '{"password":"%s"}' "$(cat "$haslo_host")")"`, putting the password in the curl process ARGUMENTS, which other processes on the host can read (ps aux, /proc/<pid>/cmdline). This defeats precisely the mechanism introduced by src/config.ts:89-101 with the rationale: 'a password provided as a container environment variable is visible in docker inspect (...) and /proc/<pid>/environ (...) With a file, inspect shows the PATH, not the value'. Furthermore, printf '%s' does not escape quotes or backslashes, so a password containing either produces invalid JSON.  
**Scenario:** Several client services share the VPS (which is exactly how the target host is described). While deploy-production.sh runs, any other user or process (even a metrics collector periodically running ps aux) can see the entire command line with the gate password in plaintext. Second variant: the password contains a quote; the JSON is invalid, the server responds 400, and the script aborts deployment with 'STOP: the gate does not accept the correct password', pointing to the wrong cause.  
**Fix:** Supply the body through stdin so it never appears in argv: `printf '{"password":"%s"}' "$(sed -e 's/[\\"]/\\&/g' "$haslo_host" | head -1)" | curl ... --data @-`. Alternatively, `curl --data-urlencode password@"$haslo_host"` with a form content type. Escaping also fixes false STOP failures for passwords containing special characters.

### [medium] A deleted message survives as a notification excerpt: the 'content really disappears' comment is false
**File:** `src/core/messages.ts:296`  
**Issue:** deleteMessage clears body and mentions rows, and the FTS trigger removes the content from the index (search actually stops finding it). But notify() previously stored a COPY of the first 160 characters in notifications.excerpt, and nothing touches it. The code comment explicitly says: 'The content really disappears, so delete means delete, not hide in the UI', which is precisely what the code does not do. react() (reaction excerpt) and markFixed() also create copies.  
**Scenario:** Alice sends bob a DM: 'card number 4111 1111 1111 1111 - delete this', realizes the mistake, and deletes the message. Confirmed by a test: body = '', search(bob,'4111') = 0 results, but listNotifications(bob) still returns excerpt 'card number 4111 1111 1111 1111 - delete this'. Bob sees the content in the notification center indefinitely, while alice sees 'message deleted' in the UI and believes the matter is resolved.  
**Fix:** In deleteMessage (within the same transaction), clear the traces: `UPDATE notifications SET excerpt = NULL WHERE message_id = ?`. Also consider deleting the notifications about this message themselves (DELETE ... WHERE message_id = ?): a notification pointing to an empty message no longer conveys information. Test: after deleteMessage, the recipient's excerpt is empty.

### [low] Limiter maps grow without bound: expired windows are never cleaned up
**File:** `src/http/routes/auth.ts:44`  
**Issue:** loginAttempts (line 44), enrollAttempts (line 59), and gateAttempts (src/http/ui.ts:169) hold one entry per client key and NEVER remove anything. An entry disappears only when the same key returns after the window expires and is overwritten; a key seen once remains in memory for the process's lifetime. This same project solves the issue correctly nearby: issueChallenge (src/core/webauthn.ts:117) sweeps expired entries on entry.  
**Scenario:** An unauthenticated attacker floods POST /api/webauthn/login/options (or /api/enroll, or /api/site-gate) from changing addresses: in IPv6 a single host usually receives an entire /64, and with trustProxy=1 the key is what the proxy adds, a different address each time. Every request adds a permanent {key -> {count, resetAt}} entry. Tens of millions of requests (hours of slow, inconspicuous traffic) mean hundreds of MB in the maps; the process ends in OOM, and the limits intended to protect the server become an attack vector.  
**Fix:** Sweep on write, exactly as issueChallenge does: at the start of each check*Limit, `for (const [k, v] of mapa) if (v.resetAt <= now) mapa.delete(k);` ('mapa' means 'map'), or every Nth call, plus a hard size cap. Extract a shared helper `okno(mapa, klucz, limit, oknoSek)` ('window(map, key, limit, windowSec)'); the same code shape is currently copied three times across two files.

### [low] POST /api/webauthn/login/options is an account existence oracle, contrary to its comment
**File:** `src/http/routes/auth.ts:181`  
**Issue:** The comment at lines 181-182 explicitly says: 'A nonexistent handle receives an empty list, not an error; the endpoint must not be an oracle for whether a user exists'. The code does something else: for an existing human with a passkey, it returns NONEMPTY allowCredentials; for a nonexistent handle, an empty list. The difference is in the response body, so the absence of an error hides nothing. The endpoint is unauthenticated (only an attempt limit precedes it), while the actor list is otherwise hidden behind authentication (GET /api/actors, line 239). It also exposes stable credential identifiers for a particular person.  
**Scenario:** An anonymous caller sends POST /api/webauthn/login/options {"handle":"michal"} and receives {"allowCredentials":["AbCd..."]}, while {"handle":"michal2"} produces {"allowCredentials":[]}. In a dozen or so requests, they build a list of real accounts on the instance and know which have passkeys, thus whom to target with phishing and whom with a password attack. Credential identifiers also allow correlation of the same person across instances.  
**Fix:** Simplest: remove the handle branch and always return empty allowCredentials; the client logs in using a discoverable credential (app.js:800 calls /login/options with an empty body, and registration sets residentKey to 'preferred'), so this branch is dead from the UI's perspective. If it must remain, return a deterministic dummy of the same shape for an unknown handle, for example HMAC(config.secret, handle) truncated to a typical credential ID length. Either way, correct the comment to describe what the code actually guarantees.

### [low] WebAuthn rpId and allowed origins come from the Host header when baseUrl is unset
**File:** `src/http/routes/auth.ts:33`  
**Issue:** Without config.baseUrl, webauthnParams builds rpId and the origin list from req.headers.host, a client-supplied header. assertOrigin (src/core/webauthn.ts:146) then compares the origin from clientDataJSON with a value derived from the SAME request, checking the request against itself; rpIdHashOk does the same. This is not a direct login bypass (the signature must still come from the victim's private key), but origin validation stops guaranteeing anything, and credentials are stored under whichever name happened to arrive in the header.  
**Scenario:** An instance is deployed without AGENTTALKS_BASE_URL (the environment variable is optional, and `agenttalks install-service` does not set it). A user visits https://atalks.example and registers a passkey, creating a credential for rpId 'atalks.example'. Another time they enter through an alias, an IP address, or a proxy that does not preserve Host: registration succeeds without complaint, but the key is bound to another rpId, and the browser will not even offer it when logging in from the canonical domain. The user sees 'passkey added', then 'I have nothing to log in with'.  
**Fix:** When config.baseUrl is empty and Host is not loopback (localhost/127.0.0.1/::1), refuse WebAuthn instead of trusting the header: `throw badRequest("webauthn_baseurl", "ustaw AGENTTALKS_BASE_URL - bez niego nie da sie bezpiecznie ustalic rpId")` ('set AGENTTALKS_BASE_URL; without it, rpId cannot be determined safely'). The Host-header path then remains where it was intended: local development. Clarify the comment above the function (lines 25-27), which currently reads like 'in dev we use Host', although a missing baseUrl is also a possible production configuration.

### [low] Malformed passkey registration data ends in 500 instead of 400
**File:** `src/core/webauthn.ts:192`  
**Issue:** After checking rpIdHash (which only requires authData.length >= 37), registerCredential reads `authData.readUInt16BE(53)` and `authData.subarray(55, 55 + credIdLen)` without checking whether the buffer has that many bytes. Likewise, cborDecode reads buf[off], buf.readUInt16BE(off), and buf.readBigUInt64BE(off) (lines 37-40) without checking the remaining length. Node then throws RangeError, which is not an AppError, so respond.fail (src/http/respond.ts:30) logs a stack trace and responds 500 'internal server error'. The rest of the module is exemplary in this respect (badRequest for every unrecognized shape), so this is a consistency gap, not a deliberate decision.  
**Scenario:** A logged-in human (or an unusual authenticator) sends POST /api/webauthn/register with an attestationObject whose authData has 40 bytes and the AT flag set: rpIdHashOk passes (>=37), the flags pass, and readUInt16BE(53) throws RangeError. The client receives 500 and does not know its data is wrong; a stack trace lands in the server log, looking like an instance failure to monitoring. Truncated CBOR has the same class of problem.  
**Fix:** Before reading: `if (authData.length < 55) throw badRequest("webauthn", "authData za krotkie")` ('authData too short') and `if (authData.length < 55 + credIdLen) throw badRequest("webauthn", "authData krotsze niz zadeklarowany credential id")` ('authData shorter than the declared credential ID'). In cborDecode, add `if (buf.length < off + n) throw badRequest("cbor", "urwane dane CBOR")` ('truncated CBOR data'). Add a test 'malformed attestationObject returns 400, not 500'; today's test/core/webauthn.test.ts covers only valid paths and wrong origin/challenge/signature/counter.

### [low] The antibot gate has no tests, despite being an access control
**File:** `src/http/ui.ts:179`  
**Issue:** siteGateBlocks, isGatedPath, gateToken, hasValidGateCookie, and checkGateLimit are full access controls (config.ts:98-101 prefers NOT STARTING to starting with an empty gate), yet the entire test/ directory contains no occurrence of 'site-gate' or 'at_gate'. startTestServer (test/http-helpers.ts) creates config without sitePassword, so 262 green tests follow only the 'gate disabled' path and never touch this code. The only verification happens in production, using curl in deploy/deploy-production.sh, after deployment rather than before.

The gate stops covering part of the UI (or covers /install and breaks onboarding for a fresh Claude Code), and nobody notices until a human report or a search engine index entry.

### [low] challengeFromClient is never read, while its comment suggests a check

### [low] Broken percent encoding in X-File-Name produces 500 instead of 400
**File:** `src/http/routes/extras.ts:149`  
**Issue:** decodeURIComponent on a client-supplied header throws URIError for an invalid sequence. This is not an AppError, so fail() logs '[http] unhandled error' and returns 500 'internal server error'. An invalid client request is reported as a server failure, precisely the distinction respond.ts describes as the reason AppError exists. ### [low] FTS query escaping is duplicated in two modules
**File:** `src/core/search.ts:35`  
**Issue:** toMatchQuery (search.ts:35-42) and the body of searchWiki (wiki.ts:378-384) contain the same nonobvious code: split on nonalphanumeric characters, remove quotes, wrap each word in quotes, and append an asterisk. The wiki.ts comment admits this explicitly ('as in message search'). This is exactly the painful kind of duplication: it is a SECURITY function (converting user text into FTS syntax), so fixing one place leaves the other path unchanged.
