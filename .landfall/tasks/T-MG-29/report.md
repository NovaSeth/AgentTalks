## Decisions
1. Reading position kept across a same-conversation `renderMain()`: `dom.js` gained `captureListPosition()` which reads `{ conv, atBottom, scrollTop }` from the `#messages` ON SCREEN (`atBottom` through the existing `isScrolledToBottom()`); `renderMain()` calls it BEFORE `el.innerHTML = ...`, stamps the new list with `data-conv="${state.activeId}"`, and hands the position to `renderMessages(position)` only when `old.conv === String(state.activeId)`. `renderMessages` uses the handed position instead of reading the fresh element (which always said scrollTop 0 / "at bottom"). The pin flag follows the same capture: `bindScrollWatch(list, atBottom)` -> `watchListPin(list, atBottom = true)`, so the ResizeObserver that fires on the fresh list (and the explicit `repinIfPinned()` after `closeThread`) does not throw a scrolled-up user to the bottom. The skeleton list (`state.loadingConv === state.activeId`) has its `data-conv` removed, so a position is never captured from a skeleton.
2. No animation on a restore: the cause was `.messages{...;scroll-behavior:smooth}` in app.css, which animated the plain `el.scrollTop = ...` assignment and every `behavior:"auto"` request. I removed `scroll-behavior:smooth` from `.messages` (it was the only smooth scroll-behavior rule in app.css) and kept `scrollBehavior(false)` returning `"auto"`: with no CSS scroll-behavior on the list, "auto" is instant for the restore, `repinIfPinned`, the unread-line `scrollIntoView` and the deep-link `scrollIntoView`. I first tried `"instant"` but the existing test `test/fixes/t-mg-8-ui-2.test.ts:321` pins the deep-link call to `behavior: "auto"` and that file is outside the brief's scope (ORC-17; changing it would also alter an existing assertion, COD-3), so the CSS removal is the contract and the new test asserts it both ways: no `scroll-behavior: smooth` anywhere in app.css and `scrollBehavior(false) !== "smooth"`. A plain re-render / re-pin / restore is a synchronous `scrollTop` assignment with nothing to animate it.
3. Smooth where intended: `scrollToBottom(true)` (jump pill, own sent message, `views.scrollToBottom(true)` in actions.js / sse-events.js / commands.js) still calls `scrollTo({ top, behavior: "smooth" })` unless `prefers-reduced-motion`; `scrollBehavior(true)` is unchanged. The reduced-motion rule in app.css (`scroll-behavior:auto!important` under `@media (prefers-reduced-motion:reduce)`) stays; its comment now says the `.messages` smooth rule is gone. Smooth scrolling no longer depends on CSS at all: it is requested per call in dom.js, as the dom.js comment already intended ("CSS alone will not stop scrollTo({behavior})").
4. A different conversation: `openConversation` sets `state.activeId` before its `renderMain()`; the old list's `data-conv` names the previous conversation, so nothing is carried over and `renderMessages()` behaves exactly as before (fresh element -> bottom), after which view-chat.js:139-143 positions at the unread line or the bottom. Re-opening the SAME conversation from the sidebar restores the old position for the intermediate render but lines 139-143 still run afterwards and put it at the unread line / bottom, as today. Test: "a DIFFERENT conversation does not inherit the old list's position".
5. No test removed, skipped or weakened; the full suite is 1050/1050 (1045 at base + 5 new).
6. Call sites of `renderMain()` checked (all direct call sites plus the `views.main()` / `views.render()` registrations in app.js): app.js:88 (boot: no old list, nothing to capture) and app.js:488 (Escape closes Details: kept); view-chat.js:69 and :79 (openConversation, skeleton then loaded: activeId already points at the new conversation, so a different conversation is not restored; the skeleton has no data-conv), :112 (openConversation, already loaded), :240/:245/:247 (Mod+. close/reopen details, profile: kept), :352 (toggleDetails: kept), :458 (details X: kept), :472 (self left the channel; same activeId, joinbar instead of composer: kept), :510 (channel edit saved: kept), :528 (conversation deleted: `openConversation(next)` or the empty state, no list), :606 is inside the edit-channel modal HTML (not a call), :678 (openDetailsAt: kept), :1965 (closeThread: kept, and the following `repinIfPinned()` honours the captured pin); view-people.js:119 and :130 (openProfile / closeProfile via `views.main()`: kept); view-login.js:73 and sse-events.js:42 (session reset via `views.render()`: state reset, no conversation); view-wiki.js:376 (wiki view, the chat column is not drawn). `openThread` does not call `renderMain` (it appends `#thread-slot` to `#main`), so `#messages` is not replaced there; `renderThread` redraws only the slot.
